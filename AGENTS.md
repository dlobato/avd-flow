# Repository Guidelines

## Project Structure & Module Organization

`src/avd_flow/` contains the Python package. `cli.py` defines the Typer commands and shared execution helpers; `__main__.py` enables module execution. Files generated by `avd-flow init` live under `src/avd_flow/resources/`, including Ansible configuration, project templates, and playbooks. Keep generated-project content in this resource tree rather than embedding it in Python strings.

Tests are in `tests/test_cli.py` and exercise command routing, resource generation, environment handling, and subprocess construction. `pyproject.toml` defines packaging and runtime dependencies; `uv.lock` pins the development environment.

## Build, Test, and Development Commands

- `uv sync`: create or update the local `.venv` from `uv.lock`.
- `uv run avd-flow --help`: run the CLI directly from the checkout.
- `uv run python -m unittest discover -s tests -v`: run all tests.
- `uv build`: build the source distribution and wheel; use this after changing package resources.
- `uv lock`: refresh `uv.lock` after changing dependencies.

For an end-to-end smoke test, initialize a temporary project, add an AVD inventory, and run `avd-flow build`. Do not run `cv-deploy` or `anta` against real infrastructure without explicit authorization.

## Coding Style & Naming Conventions

Use Python 3.11 or newer, four-space indentation, type hints, and standard-library features where practical. Use `snake_case` for functions and modules, `PascalCase` for test classes, and kebab-case for CLI commands such as `cv-deploy`. Keep command callbacks thin and route common Ansible setup through `run_playbook` and `prepare_project`.

No formatter or linter is currently configured. Keep changes consistent with surrounding code and run `git diff --check` before committing.

## Testing Guidelines

Tests use the standard-library `unittest` framework and `unittest.mock`. Name test methods `test_<behavior>`. Mock network, CloudVision, hardware, and subprocess boundaries; leave one focused regression test for each behavior change. There is no enforced coverage threshold.

## Commit & Pull Request Guidelines

History uses short, imperative commit subjects, for example `Add ANTA validation command`. Keep each commit limited to one feature or refactor. Pull requests should explain the user-visible change, list verification commands, link the relevant issue, and call out any new environment variables or external-system effects. Screenshots are unnecessary for CLI-only changes; include terminal output when it clarifies behavior.

## Security & Configuration

Never commit `.env`, credentials, tokens, generated secrets, or customer inventories. Preserve environment-variable precedence over `.env` file values. Treat deployment and hardware-validation commands as externally mutating operations.
